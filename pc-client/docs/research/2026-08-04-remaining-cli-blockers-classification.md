# Remaining Windows CLI blockers: official-source classification

Date: 2026-08-04

## Outcome

Only two of the 17 entries are immediate promotion candidates without a new complex installer module:

1. **Aider** — use the existing `python-venv` module with a managed Python 3.12 runtime and a complete, version-pinned Windows wheel lock.
2. **Augment Auggie** — use the existing `wsl-managed` module with Node 22 and the fixed npm package `@augmentcode/auggie@0.34.0`; disable its own updater so AI Hub remains the update owner.

Two more are close, but are **not** safe with the modules exactly as they stand:

- **Open Interpreter** needs a narrow `portable-binary` extension for a complete multi-file `.tar.gz` directory tree and a nested entry point.
- **Anytype CLI** has a suitable Windows ZIP artifact, but its optional Windows user-service lifecycle needs explicit stop/uninstall handling before AI Hub can claim clean removal.

Three catalog identities should be corrected before more installer work:

- **OpenManus** is a source-run agent framework, not a published standalone CLI product.
- **NanoClaw** is a WSL2/Docker self-hosted assistant checkout, not a conventional CLI package; its current canonical repository is `qwibitai/nanoclaw`.
- **AgenticSeek CLI** is only the CLI mode of the already-listed self-hosted project. Merge it into the existing self-hosted/tutorial entry rather than presenting a second installable CLI product.

Kortix has a real CLI, but its Windows `.exe` release is the **Kortix Desktop** application, not the CLI. It must never be installed through a CLI module.

## Module-fit standard used

- `npm`: fixed public npm package, supported native-Windows Node runtime, deterministic command and uninstall.
- `python-venv`: fixed Windows wheels for the full dependency graph, supported managed Python minor, no source builds or unmanaged companion runtimes.
- `portable-binary`: pinned Windows `.exe` or ZIP payload with a known entry point and ordinary directory deletion semantics.
- `managed-msi`: pinned MSI, signer/hash/product identity, known install directory and executable.
- `wsl-managed`: fixed WSL distro, managed Node/npm, fixed public npm package, isolated prefix, and fixed install script. It is not a generic WSL, Python, Go, Docker, or service-stack installer.

Dynamic `curl | bash` and `irm | iex` commands below document the vendor-supported route. They are not, by themselves, acceptable managed-install implementations: AI Hub still needs fixed versions, integrity metadata, receipts, and bounded uninstall behavior.

## Recommended promotion order

1. **Aider / `python-venv`** — lock a known Aider release and every Windows wheel against managed Python 3.12; prove install, command launch, provider-key handoff, and uninstall on a real Windows user account.
2. **Auggie / `wsl-managed`** — pin npm package and Node, disable both npm scripts and Auggie's updater, and prove WSL install, login handoff, launch, and uninstall without touching the user's unrelated WSL npm state.
3. **Open Interpreter / small `portable-binary` extension** — add only constrained, hash-verified `.tar.gz` directory extraction plus nested entry-point/alias support. Preserve the whole release tree. Do not revive the legacy Python implementation.
4. **Anytype / small lifecycle extension** — consume the pinned Windows ZIP only after service discovery, stop, and service-uninstall behavior is explicit and user data is outside the removable managed directory.

Everything else should remain tutorial/manual or blocked until its compound runtime, browser, service, Docker, GUI-control, tenant-host, or WSL-binary lifecycle is represented honestly. Installation success alone is not Windows acceptance; promotion requires real install/open/uninstall testing with the same receipt and cleanup behavior the client will ship.
