## 所有人必读

每名员工开始任何任务前都必须完整阅读：

1. `CONTEXT.md`
2. `README.md`
3. `docs/development-status.md`
4. `docs/future-development-roadmap.md`
5. `docs/incident-feedback/README.md`
6. 与本岗位相关的 ADR、协议、研究和事故记录

若文档与当前代码或用户最新决定冲突，不得自行选择其中一版。先把冲突证据报告 CTO，由 CTO 明确唯一口径并安排文档和代码同步更新。

## 共同产品与安全边界

- 厂商是第一层；同一厂商资料只保存一份，通过产品的 `directoryKind` 投影到“全部 AI 厂商”和“全部 AI 可接入厂商”。
- 同一可视化产品的官网、Web 与 Windows 入口集中在同一产品卡；CLI 是独立一级产品，并明确说明是命令行工具。
- Skill、MCP、插件和连接器按“资源类型 → 目标工具 → 资源列表 → 单项详情”展示，不回填到产品页子目录。
- 后台负责页面内容、目录关系、排序、图标、文案和已批准参数；PC 客户端负责固定本地执行模块和安全边界。
- 后台不得下发任意 EXE、Shell、PowerShell、CMD、command、args、env、headers、脚本或可执行代码。
- 新增展示数据可以只发布目录；新增本地执行原语必须升级客户端并完成独立审批。
- 手动安装的软件可以作为外部产品或可信宿主被检测、打开和辅助卸载，但没有 AI Hub 收据时不得被冒领或静默删除。
- 自动测试、隔离实包测试、用户日常机器验收和生产验收是四种不同证据，不能互相冒充。
- 任何真实用户故障都必须先搜索 `docs/incident-feedback/`，修复后更新症状、证据、根因、修复、验证、剩余验收和防复发门禁。

## 当前目录基线

- 375 个厂商。
- 614 个一级产品。
- 146 个顶层生态资源、513 个资源目标。
- 34 个固定受管 CLI；11 个候选保留官方入口并记录阻断原因。
- 首批 3 个生态资源通过 5 个宿主 profile 完成受管生命周期；其余 508 个目标保持官方说明。
- 169 个 `desktop-reviewed` 产品加 Ollama 具有固定客户端合同；另外 96 个桌面记录保持厂商官方入口。

这些数字是交接基线，不是永久常量。负责员工修改目录后必须通过脚本重新计算，并同时更新状态文档和回归测试，禁止只改写断言数字。

## 研读后发现的当前优先事项

员工研读报告发现以下问题；在解决 P0 前禁止目录发布、客户端封包或生产同步：

1. **P0：目录事实源漂移。** 当前工作区 `admin/data/catalog-v1.json` 为 614 个产品，但后台状态库报告 catalog v71、draft revision 74、草稿 615 个产品。必须先确认差异产品与唯一权威源，再通过统一事务同步，不能直接覆盖。
2. **P0：远程目录大小门禁失效。** 草稿约 1.29 MiB、活动签名目录约 1.41 MiB，而客户端远程目录读取上限仍为 1 MiB。当前活动目录不能被视为可交付状态。
3. **P0：桌面产品策略存在两套口径。** 最新用户决定是“官方直链一键下载，完成后由用户打开安装包或压缩包；无稳定直链只开官网，不回退 Winget”；旧认证、目录和部分代码仍保留强校验与 132 个包管理器合同。必须由桌面产品员工按最新决定提出迁移清单，再由 CTO 分阶段执行。
4. **P1：连接器资源类型文档不一致。** 当前代码和目录已展示连接器商店，但若干 ADR、CONTEXT 和后台文档仍只列 Skill/MCP/插件。
5. **P1：身份与社区存在旧事实源。** 当前架构规定 Flarum 是讨论、喜欢、收藏、提醒和阅读记录的事实源，但身份库仍保留旧讨论/互动表与写接口；旧 SSO 文档仍描述系统浏览器、旧数据库和旧用户名映射。
6. **P1：版本与验收文档漂移。** 当前源码为 0.1.40，但开发状态、验收清单、事故记录和 Git 标签仍分别停留在旧版本；历史测试不能自动继承为 0.1.40 的验收证据。

## 协作流程

1. CTO 把任务发送给唯一主责员工，并写清目标、范围、验收和禁止事项。
2. 主责员工先阅读公共文档、岗位文档和同类事故记录，再报告影响文件与跨员工依赖。
3. 员工不得直接跨职责大改；需要另一个模块时报告 CTO，由 CTO 给协作员工发送明确子任务。
4. 主责员工保留现有未提交修改，不得 `reset --hard`、覆盖用户文件、删除未知文件或重建整个目录。
5. 主责员工完成实现和聚焦测试后，向 CTO 报告改动、证据、失败项和真实验收缺口。
6. CTO 再派“测试发布运维”执行跨模块回归。未收到明确发布指令时，不封包、不上传云端、不切换生产。
7. 发布员工只验证集成和制品，不替代功能员工修业务逻辑；发现问题退回主责员工。

## 模型调度

模型按任务风险动态指定，不永久绑定，也不默认使用最高推理强度：

| 员工窗口 | 默认模型 | 默认推理 | 使用理由 |
| --- | --- | --- | --- |
| AI商店前端 | `gpt-5.6-terra` | `medium` | 日常 React、状态与接口接线 |
| AI商店设计 | `gpt-5.6-terra` | `medium` | 产品结构、交互规格与视觉验收 |
| AI商店后台 | `gpt-5.6-terra` | `high` | schema、发布事务与权限边界 |
| 厂商产品目录 | `gpt-5.6-terra` | `medium` | 官方资料研究、分类、去重与内容维护 |
| 桌面产品管理 | `gpt-5.6-sol` | `medium` | Windows 安装、任务并发、收据和卸载风险 |
| CLI一键部署 | `gpt-5.6-sol` | `medium` | 多运行时、WSL、命令执行与所有权风险 |
| 其他产品 | `gpt-5.6-terra` | `high` | 多宿主协议、权限与资源适配 |
| 个人中心 | `gpt-5.6-sol` | `medium` | 身份、会话、隐私与敏感变更风险 |
| AI商店社区 | `gpt-5.6-terra` | `high` | Flarum、SSO 与跨服务数据一致性 |
| 测试发布运维 | `gpt-5.6-sol` | `medium` | 制品、版本、回滚和生产变更风险 |

简单文案、资料整理或机械更新可以临时降为快速模型；复杂事故或架构审计可以由 CTO 临时提高推理强度。每次 CTO 派单时显式指定模型和推理等级，避免依赖线程旧设置。

## 交接报告格式

员工每次完成任务时必须报告：

- 完成了什么。
- 修改了哪些文件和接口。
- 没有修改哪些相邻模块。
- 执行了哪些自动验证，结果是什么。
- 哪些真实用户或生产验收仍未完成。
- 是否产生了跨员工依赖、文档冲突或兼容性风险。
- 建议下一步由哪名员工接手。
