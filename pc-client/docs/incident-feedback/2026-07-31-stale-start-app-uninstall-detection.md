# 桌面产品卸载后被开始菜单残留误判

## 现象

Claude Desktop 点击卸载后没有出现可见面板，客户端长期显示“卸载程序已打开”，
并持续确认卸载结果。

## 真实设备证据

- Claude 的注册表卸载项已经消失。
- `Claude.exe` 和 `Update.exe` 进程均不存在。
- Windows `Start Apps` 仍残留
  `com.squirrel.AnthropicClaude.claude`。
- 持久化桌面操作任务因此连续把产品判定为 `installed`。

这说明 Claude 的 Squirrel 卸载器已经自动完成卸载；“没有弹出面板”不是启动
失败。

## 根因

旧检测器把注册表安装项、Appx 包身份和开始菜单入口视为同等级证据。对已经审核
安装身份的桌面产品而言，开始菜单缓存只能用于启动，不能单独证明产品仍然安装。

界面同时把所有卸载适配器都描述成“已打开卸载程序”，没有区分静默自动卸载和
需要用户操作的厂商卸载面板。

## 通用模块修复

- 每个桌面适配器必须声明 `presenceEvidence`：
  - `trusted-install-identity` 只接受可信注册表项或可信 Appx 包；
  - `discovery` 才允许使用开始菜单入口作为安装证据。
- 每个桌面适配器必须声明 `uninstallMode`：
  - `automatic` 显示“正在自动卸载”；
  - `interactive` 显示“已调起厂商卸载面板”，并提示手动完成。
- 检测器、持久化任务和界面统一消费模块元数据，不按 Claude 产品 ID 写特例。
- 已审核产品的可信安装身份消失后，即使开始菜单仍有残留，也确认产品已卸载。

## 验证

- 回归测试覆盖“注册表和 Appx 均消失、开始菜单仍残留”的真实故障形态。
- 契约测试要求所有托管桌面适配器声明安装证据策略和卸载交互模式。
- 自动卸载文案测试保证不会承诺出现面板或要求手动完成。
- 手动卸载文案测试保证明确提示用户在厂商面板中完成。
- 完整单元测试和生产构建通过后才生成更新包。

## 用户验收

安装修复版本后，Claude 当前状态应直接恢复为未安装。
