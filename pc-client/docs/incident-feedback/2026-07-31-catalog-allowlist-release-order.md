# 目录发布与客户端白名单版本错位

日期：2026-07-31

## 用户可见问题

客户端白名单已经修改，但 Docker 后台仍运行旧镜像或持有旧草稿。直接重建时，旧草稿可能不符合新白名单；直接写入时，新目录又可能不符合旧镜像白名单，形成发布顺序死锁。

## 根因

此前发布依赖人工顺序：修改目录、修改白名单、重建后台、写草稿、发布。这个流程没有把旧 revision 的兼容替换作为原子步骤，也没有在重建前保存待发布目录，因此容易出现后台覆盖本地文件或新旧校验器互相拒绝。

## 固定处理

新增 `npm run catalog:publish:local`：

1. 先用当前源代码白名单验证待发布目录。
2. 从 revision store 读取旧草稿 revision 和活动版本，不要求旧草稿通过新策略。
3. 重建并启动包含新白名单的后台镜像。
4. 只等待无目录副作用的 `/health`，随后用旧 revision 精确替换草稿。
5. 调用后台发布前校验并发布。
6. 最后要求 `/ready` 的草稿 revision 和活动目录版本与本次结果完全一致。

后台 `release-store` 已支持“精确 revision 替换被新策略淘汰的旧草稿”；新脚本固定使用这条迁移路径，不再添加临时产品白名单。

## 回归门槛

- 源代码目录校验通过。
- 342 项单元/策略测试通过。
- Docker 后台 `/ready` 同时返回目标 draft revision 与 catalog version。
- 发布后的 `/catalog-release.json` 必须能被客户端签名校验器接受。
