# Windows 桌面目录重放产生策略与文案漂移

日期：2026-08-04

## 现象与证据

重新应用 Windows 桌面扩充、直装白名单和包管理器策略时，Jan 一度同时保留“官方入口”策略和旧托管 `download` 字段，目录校验失败。修复该字段后，全量测试又发现 Canva 与 DuckDuckGo 的后续规范名称被早期基线或包管理器短标签覆盖。无内容变化的重复执行还会刷新 `updatedAt`，导致目录文件哈希无意义变化。

## 根因

三个脚本分别读取并直接写同一个正式目录，日常流程没有单一入口。早期扩充脚本使用合并语义，切回官方基线时不会自动清除旧托管字段；下游内容修正与执行策略由不同脚本负责，人工重放顺序遗漏时会暴露中间状态。每段都无条件写入和更新时间，无法区分语义变化与普通重放。

## 修复

- 官方桌面基线覆盖已有产品时显式删除不存在于定义中的托管 `download`。
- Canva 与 DuckDuckGo 恢复各自上游规范展示名，不再使用包管理器短标签覆盖产品文案。
- 新增统一 `catalog:apply:windows-desktops` 入口，在临时目录副本按固定顺序应用三段策略，最终通过完整目录校验后才一次提交。
- 任一步失败只删除精确临时文件，不修改正式目录；忽略 `updatedAt` 后没有语义变化时不写正式文件，目录哈希保持不变。
- 最终包管理器阶段写入前运行 `validateCatalog`，防止非法中间策略进入正式目录。

## 自动验证

事务流水线测试从故意损坏的名称开始，确认一次执行恢复规范目录；第二次执行返回 `changed: false`，文件内容逐字节不变。目录、搜索、安装白名单、所有权收据与下载通道测试共同验证 375 个厂商、615 个产品、169 个 `desktop-reviewed` 产品及 37 个直装下载入口。

## 剩余人工验收

该修复只证明目录生成与客户端策略一致，不代表 170 个受管 Windows 产品已经在真实用户账户完成安装、打开、更新和卸载验收。

## 防复发门禁

Windows 桌面目录维护只运行统一事务入口，不再手工串联底层脚本。任何目录重放都必须同时满足：最终目录校验通过、搜索身份断言通过、无 dossier 产品不获得执行能力、无语义变化时文件哈希不变。
