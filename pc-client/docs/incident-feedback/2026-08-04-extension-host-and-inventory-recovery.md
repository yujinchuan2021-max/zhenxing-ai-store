# 资源宿主识别与已安装清单恢复

## 现象

- Claude Code 插件的主收据丢失、但宿主内的冗余实例标记仍在时，资源详情可以识别异常状态，“已安装”页却不会列出，用户失去修复或保守卸载入口。
- 用户手动安装的 Codex CLI、Claude Code 或 Cursor 可以正常运行，但资源安装仍显示“宿主缺失”。
- 同一个远程 MCP 只有 Codex 配置适配，Claude Code 与 Cursor 只能打开说明，容易让多宿主资源退化成重复的手工教程。

## 根因

- 已安装清单先按主收据文件过滤 profile，跳过了 Adapter 自己的恢复证据。
- 宿主发现只接受枕星 AI 的产品安装收据，没有独立的可信外部宿主只读发现。
- MCP 配置曾被当作单一宿主实现，而不是“统一资源 + 每个宿主独立 profile/收据”。

## 修复

- 已安装清单枚举全部客户端固定 profile，再由对应 Adapter 判断是否为受管或异常状态；主收据不再是进入清单的前置条件。
- 宿主发现优先使用枕星 AI 受管实例，并以绝对路径、realpath、固定产品布局与 Authenticode 签名只读识别用户手装 Codex/Claude；Cursor 复用已审核桌面身份探针。外部宿主只提供加载能力，不获得产品卸载所有权。
- OpenAI Developer Docs MCP 保持一份资源资料，新增 Codex、Claude Code、Cursor 三个独立固定 profile。Claude 使用官方 user-scope CLI，Cursor 只原子合并 `~/.cursor/mcp.json` 的固定键；各自独立收据，同名外部配置不覆盖。
- Claude Code 没有稳定的非交互启停合同；Cursor 的 Agent CLI 尚未进入本地签名准入。因此本轮不显示虚假的启用/停用按钮。

## 预防门

后续资源宿主必须满足：固定本地 Adapter、可信宿主身份、独立目标 profile、当前签名目录重新授权、收据或冗余实例标记恢复、同名外部内容冲突保护和保守卸载。后台不得传入命令、参数、环境变量、请求头或本地路径。没有真实宿主合同与验收的资源继续显示“打开官方说明”，不得只改后台字段就变成一键安装。
