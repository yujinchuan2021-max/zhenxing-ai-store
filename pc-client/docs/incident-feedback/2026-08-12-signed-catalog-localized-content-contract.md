# Signed catalog localized content contract

## Symptom

Switching the desktop language to English translated fixed interface copy, but
signed catalog content such as banners, vendors, products, and resources still
rendered the single Chinese value stored in active catalog schema v2.

## Evidence

- Catalog objects exposed only their primary display fields; there was no
  signed locale-specific value for the renderer to select.
- Exact-field validators rejected an added `localized` record before the
  catalog could reach the Admin draft store or signed release pipeline.
- Admin draft storage, canonical signing, release verification, and remote icon
  projection already preserve validated JSON fields; they did not require a
  second localization adapter.

## Root cause

The backend contract distinguished interface language from catalog content
language. The renderer could translate fixed controls, but the catalog schema
had no authenticated English content to render.

## Fix

Schema v2 now accepts one optional, exact `localized.en` record on the existing
display objects:

- home banner: `eyebrow`, `title`, `description`, `action`
- carousel slide: `imageAlt`, `title`, `description`
- carousel action: `label`
- vendor, product, and resource: `name`, `description`
- resource store: `label`
- brand: `slogan`
- extra section: `title`
- community: `title`, `description`

When present, each English record must be complete, contain no unknown fields,
and obey the same length bound as its primary field. Catalogs without
localization remain valid. Schema v1 does not gain new localized fields.

No translation is generated by the backend. The primary values remain the
Chinese source, and English content must be authored and reviewed before a
future signed publication.

Frontend DTO selection is identical for every supported object type:

```ts
const localized = language === "en" ? value.localized?.en : undefined;
const displayed = localized?.field ?? value.field;
```

The exact DTO records are:

- `Brand.localized.en`: `{ slogan }`
- `ExtraSection.localized.en`: `{ title }`
- `Community.localized.en`: `{ title, description }`
- `CatalogBanner.localized.en`: `{ eyebrow, title, description, action }`
- `HomeCarouselSlide.localized.en`: `{ imageAlt, title, description }`
- `HomeCarouselAction.localized.en`: `{ label }`
- `Vendor.localized.en`, `Product.localized.en`, and
  `Resource.localized.en`: `{ name, description }`
- `ResourceStore.localized.en`: `{ label }`

`resource.publisher` remains a publisher proper name. `categories` and
`product.category` remain stable classification keys used by filtering and
equality checks. Brand `name` and community `provider` likewise remain proper
names. None of these values are translated or replaced by localized display
copy in this contract.

## Verification

The focused contract test follows one catalog through validation, Admin draft
save/read, Ed25519 publication and verification, and remote projection. It also
proves that changing localized content after signing invalidates the envelope,
and that partial, extra, empty, unknown-locale, and overlong records fail
closed.

## Remaining acceptance

- Content owners must supply reviewed English values for every object intended
  to render in English. This change does not modify active state or publish a
  release.
- Frontend must select `localized.en` only for English and otherwise use the
  primary field. Missing localization therefore has an explicit fallback, not
  machine translation.
- A later publication requires the ordinary Admin review, signature, and
  release acceptance gates.

## Prevention gate

Any future localized display field must enter this single signed catalog
contract, survive the Admin draft round trip, and be covered by signature
tamper and remote-projection tests. Product-specific renderer exceptions and
unsigned translation overlays are not accepted.

## Frontend consumption

The renderer now uses one pure `catalogDisplayField(value, field, language)`
selection seam for every field listed above. English selects the signed
`localized.en` value; Chinese and missing English records use the primary
field. The helper does not mutate catalog objects, translate text, or change
stable identifiers, categories, brand names, community providers, publishers,
URLs, or execution inputs.

The visible consumption paths cover the home banner and carousel (including
action labels and accessible image text), brand slogan, extra navigation,
anonymous community introduction, vendor directories/details, product rows,
resource stores/details, search results, task display names, and Workflow
Composer product labels. Existing active7 data contains no populated
`localized.en` records, so it remains fully compatible and intentionally
falls back to its primary fields.

The renderer evidence is now explicit rather than representative. One
table-driven test enumerates all 19 display fields in the backend contract and
proves English selection, Chinese primary values, per-field missing-English
fallback, active7 compatibility, and deep input immutability. Its coverage
gate was red at 10 records and green at 19.

The existing no-output Electron fixture was then made red by requiring the
carousel secondary action from the real built renderer. Its green path drives
the real App through `zh -> en -> zh` and checks banner, carousel title,
description, image alt and both action labels, brand, extra section, community,
vendor, product, resource, store, task name, and Workflow Composer. Visible
records remain singular, old-language values disappear, the internal primary
action route and signed secondary URL stay unchanged, and catalog DTOs compare
deeply equal before and after rendering. The same fixture exercises the
localized home, banner, and Workflow Composer at 740px; broader 740px layout
coverage remains the existing queue/store fixture boundary and is not claimed
as a packaged-client acceptance pass. No screenshot output is written.

Focused renderer/carousel/language tests and the production build are the
local verification boundary. Fixture and build success do not replace a
packaged-client or real-user language switch.

Content remains the outstanding dependency: no English catalog values were
authored, saved, signed, or published in this frontend change. Content owners
must populate and review the signed fields before an English release can avoid
primary-field fallback everywhere. Isolated automation does not replace a
packaged-client or real-user acceptance pass.
