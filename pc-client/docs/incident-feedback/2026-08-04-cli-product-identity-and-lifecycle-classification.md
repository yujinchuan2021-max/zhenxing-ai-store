# CLI 产品身份与生命周期误判

## 现象

目录把部分“可以在终端里运行的源码项目”直接标成独立 CLI 产品，并把
厂商发布页上的 Windows EXE 默认理解为 CLI。这样会让用户看到并不存在的
一键安装承诺，也会把 Docker、浏览器、服务或 WSL 依赖遗漏在卸载收据之外。

## 根因

旧扩充流程主要依据名称、README 关键词和资产扩展名归类，没有逐项确认：

- 是否存在厂商正式发布的 CLI 身份和命令入口；
- Windows 支持是原生、WSL、Docker 还是仅教程；
- 发布物是否真的是 CLI，而非同厂商桌面客户端；
- 安装后还会创建哪些服务、浏览器、容器、计划任务和用户数据；
- 当前客户端模块能否完整检测、打开、更新和卸载这些组成部分。

## 修复

- 以官方文档、仓库、包注册表和真实发布物重新核对剩余 CLI。
- OpenManus、NanoClaw 改为源码/部署教程，不再冒充独立 CLI。
- AgenticSeek 的重复 CLI 卡并回既有自托管产品。
- Kortix 明确区分 macOS/Linux CLI 与 Windows 桌面 EXE。
- Aider、Open Interpreter 只有在固定 Python/归档、版本探针和收据卸载闭环完成后才升为受管产品。
- Anytype 即使固定 ZIP 已核验，仍因 Windows 用户服务归属无法由当前收据证明而保持官方入口。

## 预防门

以后新增或升级 CLI 必须先形成产品级审计记录，至少包含：产品身份、Windows
支持形态、固定版本与产物、依赖、安装副作用、启动入口、更新归属、卸载
范围和保留数据。只有现有客户端固定模块能够拥有完整生命周期时才允许
`cli-managed`；源码项目、复合服务和动态租户安装器保持教程/官方入口。

后台只能引用已批准 profile，不能通过修改字段把被阻断产品变成可执行模块。
