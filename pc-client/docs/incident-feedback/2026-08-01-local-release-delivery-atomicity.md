# 本地发布交付与回滚原子性问题

日期：2026-08-01

## 用户可见现象

重复生成同一版本时，`release-local-server-client` 可能混入上次构建文件；复制或清理中途失败时，目录可能只更新了一部分。Setup 的 blockmap 没有进入 SHA-256 清单。发布命令即使返回清理待处理，也可能仍报告成功。验收失败后的服务回滚还可能留下首次生成、但已被拒绝的 Docker 镜像。

## 根因

- 打包脚本逐个覆盖正式目录，没有先形成并验证完整候选交付物。
- 交付目录切换不在验收事务内，旧运行时回滚后仍可能保留新安装包。
- 目录切换前没有持久事务收据，进程在两次重命名之间退出时缺少精确恢复依据。
- 激活和旧目录恢复同时失败时，打包脚本的 `finally` 仍可能删除唯一候选目录。
- finalize/rollback 无条件附加 `ok: true`，掩盖清理锁、staging 和 retired 目录的待处理状态。
- Docker 镜像检查把任意非零退出都当成“镜像不存在”，会把守护进程或权限故障误判为安全状态。
- 首次发布没有旧镜像时，回滚只删除容器，没有删除并复核被拒绝的新镜像标签。

## 修复

- 在正式目录同级生成候选目录，只接受 Setup、Portable、Setup blockmap、BUILD.json 和 SHA256.txt 五个文件。
- BUILD.json 绑定三个二进制产物；SHA256.txt 覆盖三个产物及 BUILD.json，任何缺失、额外文件或哈希漂移都会在切换前失败。
- 在第一次目录重命名前原子写入严格事务收据，记录旧目录和新目录的逐文件大小与 SHA-256 快照。
- 打包交付、运行时发布和三个本地应用服务镜像共用同一次验收事务；验收失败会分别恢复，任一恢复不确定都会保留收据并停止全部相关服务。
- 支持恢复“旧目录已移入 retired、候选尚未切换”的崩溃窗口；激活与恢复双重失败时保留候选和 retired 两份唯一恢复数据。
- retired 清理失败会返回非零并保留可重试收据；清理成功后才允许删除收据。
- 发布准备、finalize 和 rollback 统一从所有 `*CleanupPending` 字段推导 `ok`，不再伪报成功。
- Docker 仅把明确的 `no such image`、`no such object` 或镜像级 `not found` 当作不存在；其他非零结果直接失败。
- 首次发布回滚会删除容器、强制删除被拒绝的服务镜像标签，再次检查其确实不存在。
- 正式打包要求 Git 工作树干净，且当前提交具有与 `package.json` 完全一致的版本标签。
- 主事务在三份子事务都完成验收后封存 delivery、runtime、services 收据的 SHA-256；进入 accepted 以及每个破坏性 finalize 前都会重新核对，收据内容被替换时不允许用语义较弱的恢复分支继续收尾。
- 三个自建服务先从精确 Git 提交生成离线候选镜像，再核对提交标签、版本标签、运行契约和所有直接复制源码的逐文件 SHA-256；通过后才允许替换活动镜像。
- identity 当前镜像固定读取后台活动 URL，同时 Compose 保留只读 `admin/data` 文件契约，使旧版 file-based identity 镜像回滚后仍能启动；缺少任一契约都会在发布前失败。
- 首次发布失败不但复核被拒绝的镜像已经删除，也复核对应容器已经不存在。

## 回归门槛

- 收据必须先于第一处目录切换存在，崩溃窗口可以幂等回滚。
- 同版本残留、缺少 blockmap、SHA 清单漏项、哈希不一致或额外文件必须被拒绝。
- 激活和恢复同时失败后，候选、retired 和收据必须全部保留。
- 任何清理或恢复不确定状态必须返回非零、保留收据并停止相关服务。
- 无旧镜像的服务回滚后，新容器和新镜像标签都不得残留。
- Docker 守护进程、权限或上下文错误不得被解释为镜像不存在。
- accepted 主事务必须拥有三份完整封存哈希；封存后任一收据发生字节变化，接受或收尾都必须失败并保留现场。
- 自建镜像必须来自同一带版本标签的干净 Git 提交，且容器内受管源码哈希必须与该提交清单逐项相同。
- 当前 identity URL 契约、旧 identity 文件契约和只读兼容挂载必须同时存在，防止发布成功后旧镜像无法回滚。

## 验收边界

自动化覆盖目录结构、来源标签、哈希清单、事务崩溃恢复、清理重试、命令退出语义和 Docker 回滚脚本。最终 Windows Setup/Portable 的真实安装、升级与卸载仍需在日常 Windows 用户账户中人工验收。
