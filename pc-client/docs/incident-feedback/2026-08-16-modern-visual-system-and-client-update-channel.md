# 现代视觉系统与客户端更新通道

## 用户反馈

旧客户端仍使用高饱和青绿色、橙色选中边框、字符图标和密集卡片，整体缺少当代桌面软件的层次感。客户端版本信息也只存在于设置页，用户无法在主界面直接看到自动检查结果或在确有新版本时发起更新。

## 根因

- 顶栏、侧栏、筛选器与资源卡片长期由多轮局部 CSS 叠加，没有统一的视觉令牌和组件层级。
- 主导航使用 Unicode 字符模拟图标，尺寸、笔画和对齐无法统一。
- 更新检查虽然已在客户端启动时自动执行，但结果只在设置页展示，主工作流没有状态入口。
- 生产部署拓扑没有统一公开 `/update-release.json`，即使未来生成签名更新清单，客户端也缺少一致的服务器路径。

## 修复

- 保留现有 Electron、React 和业务模块，引入固定版本的 Tabler Icons React，只替换图标层，不重写成熟运行时。
- 新增午夜蓝、电光青和薄荷绿视觉令牌，统一顶栏、导航、按钮、筛选器、卡片、焦点与响应式布局。
- Skill、MCP、插件和连接器继续使用同一资源商店模块；新资源类型会自动复用统一的图标、卡片和筛选布局。
- 顶栏新增客户端版本状态。启动时沿用现有自动检查；只有签名清单确认存在新版本时才显示“立即更新”，最终安装仍须用户明确点击。
- 三种服务器拓扑都将 `/update-release.json` 交给 Admin 只读发布边界，客户端更新清单请求改为不跟随重定向、精确最终 URL、固定来源和严格 JSON Content-Type。

## 安全与发布边界

- 页面不能下发任意下载地址、命令、请求头或凭据；更新包仍由签名清单、下载来源、哈希和 Windows 签名校验控制。
- 自动检查不等于自动下载或自动安装。客户端启动不会运行安装器。
- 当前生产更新通道仍保持 disabled：仓库没有可公开信任的正式更新签名公钥，也没有本轮正式代码签名安装包。不能用占位 key 或未签名包伪造启用状态。
- 本轮只修改源码与服务器配置模板，没有封包、安装、部署、签名或发布。

## 验证与防回退

- 聚焦测试锁定 Tabler 依赖、真实图标、自动更新状态、明确更新动作、统一资源布局和服务器更新路径。
- 更新网络测试继续锁定手动重定向、允许来源、响应大小和签名验证边界。
- Vite production build、Lint、Node 语法检查及浏览器视觉对照必须同时通过。
- `design-qa.md` 固定选定视觉稿、验证视口、差异说明和最终结果，避免后续局部样式重新退回字符图标或旧高饱和配色。

## 剩余正式验收

生产启用须另行完成：生成并妥善保管更新签名私钥、把公钥写入客户端通道、构建正式代码签名安装包、生成签名更新清单、部署到 HTTPS 路径，并在旧版实机上验证“自动发现 → 用户点击 → 受控下载 → 校验 → 安装”。
## 资源详情行信息密度修正

资源详情行曾把类型、标题、说明、治理标签、风险提示、兼容性、版本、安装范围、卸载方式、核验日期和最多三个外部操作塞进一个紧凑的三列横条。底层事实没有错误，但 `3px` 的内部间距和可换行的内联事实列表，会让本来无关的内容在常用桌面视口下读起来像一整段文字。

新布局保留全部事实与操作，只重新明确视觉职责：类型与标题组成标题区，说明使用独立的可读行高，治理状态保持标签组，受限提示成为单独提示块，决策事实使用响应式网格。外部操作继续位于独立操作列，并在已有响应式断点下落到内容下方。本次没有修改目录、来源、审核、风险、兼容、安装或执行合同。

聚焦回归最初因为资源行缺少四个结构类和网格事实布局而失败。修正后，现代外壳与相关资源商店测试 13/13 通过，`npm.cmd run build` 与 `npm.cmd run lint` 通过；重新打开用户反馈中的资源详情状态后，标题、治理、提示、事实和操作不再互相挤压。构建中既有的 Node 模块浏览器外置和大包警告与本问题无关。

后续资源详情改动必须继续把标题、摘要、治理/提示、事实和操作分开。新增持久事实应进入事实网格或可展开的技术详情，不得重新退化为没有层级的内联文字流。

## 产品、已安装与环境卡片信息层级修正

### 症状与证据

- 产品卡把类型、标题、说明和多条使用提示连续排列，操作区虽然独立，但正文缺少明确的主次分组。
- 已安装卡把版本、路径、更新归属、可用版本、推荐版本和运行消息都作为同一种红色小字展示，用户难以区分普通事实、更新机会和错误。
- 设置中的环境卡将每个操作按钮单独拉成整行，推荐版本与状态被挤进很窄的文字列；用户截图中“审核推荐版本”已纵向断裂。

### 根因

三个视图各自沿用早期的扁平 DOM 和通用 `small` 样式，没有把身份、状态、技术信息与操作定义为稳定的视觉区域。环境卡的直接子按钮规则还强制 `width: 100%`，放大了堆叠问题。

### 修复

- 产品卡增加主信息和状态提示两层，操作继续独立置于卡片右上方。
- 仅对首要的已安装产品卡增加身份、技术信息和状态栈；更新机会使用现有强调色，普通运行状态不再继承错误红色。其他资源与安装包卡片的错误语义保持原样。
- 环境卡把名称/检测状态、操作组、推荐版本和运行消息分区；操作在一行内自然换行，不再逐个占满整行。
- 窄屏下管理页标题与操作改为上下排列，避免标题、说明与刷新按钮互相压缩。
- 没有修改安装、更新、打开、卸载、下载或后台发布判断。

### 验证

- 新增聚焦门禁先因结构类缺失失败，修复后相关 51 项前端测试通过。
- TypeScript production build 与 lint 通过。
- Electron 数据夹具在 1365 和 740 视口均无横向溢出，所有操作按钮位于视口内；环境设置夹具渲染 2 张结构化卡片，控制台错误为 0。
- `design-qa.md` 记录了用户截图、产品前后对比、已安装宽/窄视口和环境设置局部截图，最终结果为 passed。

### 剩余验收与防回退

真实电脑上的已安装软件数量、路径长度和厂商名称仍可能比夹具更长；正式封包后的实机验收仍需检查这些真实数据。本地浏览器预览没有本机安装数据，不能把空态浏览器截图写成已安装卡片实机通过。后续新增卡片事实必须进入身份、状态或技术信息区域；不得恢复“所有 `small` 都是错误色”或“每个按钮强制整行”的通用规则。

## Mantine 9 第二阶段 AppShell 与紧凑筛选

### 范围与根因

第一阶段只接入主题、命令中心、通知和下载弹层，主页面几何仍由旧的顶栏/侧栏网格负责；窄屏下重复的筛选标签会占用大量纵向空间。第二阶段仅把外壳几何交给 Mantine `AppShell`，并为同一组筛选值增加窄屏 `Select` 呈现，不迁移业务状态。

### 实现与所有权

- `AppShell.Header`、`AppShell.Navbar`、`AppShell.Main` 复用原顶栏、导航和内容节点；所有按钮继续调用原有 `navigate`、厂商、产品、资源商店、已安装与设置 handler。
- 移动导航只新增一个本地开关状态。Navbar 使用 `useMediaQuery` 明确选择最终 `translateX`，避免把正确性依赖于隐藏 BrowserWindow 不会稳定推进的过渡帧；没有第二套路由或导航事实源。
- `FilterRow` 只把原 `values` 映射为 Mantine `Select` 数据；桌面标签与窄屏下拉共用同一个 `active` 值和 `onChange`，不会产生两份筛选状态。
- 目录、审核、下载、安装、更新通道、客户端版本和服务器接口均未修改。

### RED → GREEN 与验证

- 第二阶段聚焦测试先因缺少 `AppShell`、Burger 和紧凑筛选 seam 失败；最小接入后 7/7 通过。
- 窄屏 Electron 夹具随后暴露隐藏窗口会暂停侧栏过渡，导致只看截图可能把旧帧误判为当前状态。夹具现仅在测试 DOM 内关闭过渡，并验证关闭/打开/再次关闭的最终几何、主内容从视口左缘开始、紧凑筛选显示和标签组隐藏。
- 相关现代外壳与资源商店测试 33/33 通过；Vite production build、lint、Node 语法、diff check 通过。
- in-app Browser 在 1280 x 720 的真实 Skill 商店状态无控制台错误、无横向溢出、可见按钮全部位于视口内；参考稿与最终实现已放入同一比较图并在 `design-qa.md` 记录为 passed。

### 防回退与剩余边界

后续页面若采用 AppShell 或紧凑筛选，必须继续复用原导航 handler 和筛选状态，不得复制目录或安装事实。旧的完整资源夹具还假设每个 Skill 数据集都有 `research` 场景和 `agent` 兼容项；这与当前夹具数据不一致，属于既有独立测试债务，本阶段没有通过删除断言来伪造全量通过。

## Mantine 9 第三阶段设置、账号表单与批量更新

### 范围与所有权

- 设置页由 Mantine Drawer 承载，继续调用原主题、语言、目录、任务、环境和客户端更新 handler。
- 登录/注册由 Mantine Modal、TextInput 和 PasswordInput 呈现；账号、验证码和密码仍只交给既有 `window.aihubPC` 接口，本阶段没有新增服务、存储或认证策略。
- 已安装页的“全部更新”继续调用唯一的 `updateAllInstalled`，只增加 Mantine loading 反馈，没有复制扫描、审核、发布或更新执行逻辑。
- 新增的“关闭”文案在中英文语言资源中成对维护，关闭按钮使用 Tabler `IconX`，不再使用文本字符充当图标。

### 现场问题与根因

第一次真实浏览器验收发现登录文本框几乎不可见，设置卡片边框退化为黑色。根因不是 Mantine 输入组件本身，而是 Drawer/Modal 通过 Portal 渲染到 `.pcApp` 外部；仅定义在 `.pcApp` 上的 `--surface`、`--line`、`--ink`、`--cyan` 等变量无法继承。包含未定义变量的后置 `color-mix` 声明在计算阶段失效，边框因此回到初始颜色。

### 修复与防回退

- 把选定的浅色视觉令牌同步到 `:root`，把深色令牌同步到 `html[data-mantine-color-scheme="dark"]`；`.pcApp` 仍保留原主题边界，普通页面视觉不改变，Portal 获得同一套事实。
- 表单样式改为明确作用于 Mantine Input 和 InputWrapper 公共类，标签、必填标记、说明、边界和背景不再依赖旧的原生 `label > input` 结构。
- 测试锁定 Drawer、Modal、TextInput、PasswordInput、批量 loading、Portal 根令牌和原服务调用。任何把令牌重新只放回 `.pcApp` 的修改都会让聚焦测试失败。
- 隐藏 Electron 不稳定推进 Drawer 和响应式 Navbar 过渡；夹具只在测试 DOM 内关闭相应过渡并等待最终几何。完全位于视口外的关闭式导航不再被误称为“可见按钮”，任何部分进入视口却被裁切的按钮仍会失败。

### 验证与剩余边界

聚焦与相关回归 58/58、构建、Lint、已安装宽窄屏夹具和下载队列夹具均通过；真实浏览器确认浅色/深色 Drawer、可见的 42 px 登录字段、Escape 关闭、页面无横向溢出且控制台错误为 0。视觉验收没有提交登录/注册表单，也没有触发真实软件更新；认证与更新执行仍需由对应后端和发布合同独立验收。

## 资源商店固定筛选栏与独立结果窗口

### 症状与根因

Skill 商店的筛选条件和资源卡片原本共享页面滚动。资源较多时，用户查看后续卡片会丢失当前来源、宿主和兼容级别上下文；详情页又在资源名称上方重复一次“Skill 商店”。MCP、插件和连接器共用同一页面模块，因此若只在 Skill 页面写特例，后续四种体验会再次分叉。

根因是资源商店只定义了两列网格，没有给页面、筛选列和结果列建立明确的高度与滚动所有权；详情标题仍保留早期的类型 eyebrow，和新的商店 Hero 形成重复信息。

### 修复与所有权

- 共享 `ResourceStorePage` 现在提供一个受视口约束的资源窗口；筛选栏和结果栏各自拥有纵向滚动，结果区滚动不会移动筛选栏或文档。
- Skill、MCP、插件和连接器全部复用相同 DOM seam 与响应式 CSS，没有按商店复制状态或样式。后续接入同一资源商店模块的新类型也自动继承此布局。
- 结果顶部的来源摘要在结果窗口内保持可见；桌面与中等宽度维持左右分栏，640 px 及以下回到单列文档流。
- 详情页只删除资源名称上方重复的商店 eyebrow；列表卡片上的类型徽标仍保留，目录、筛选、资源事实与操作没有变化。

### RED → GREEN 与防回退

- 聚焦测试先因缺少有界资源窗口、独立滚动 seam 和详情去重断言失败；实现后现代 UI 10/10、相关资源联合测试 22/22 通过。
- 真实 in-app Browser 对四个商店逐一验证相同分栏。Skill 结果区从 0 滚到 500 时，筛选栏位置和文档滚动均保持不变；连接器详情的重复标题计数为 0。
- Electron shell-only 夹具在 1365/740 两个视口验证有界高度、左右关系、结果可滚动、筛选位置不变和文档不滚动。夹具在截图前等待 AppShell 最终几何，避免隐藏窗口 resize 后的旧合成帧造成假视觉证据。
- 构建、Lint、Node 语法和 scoped diff 检查通过。旧全量资源夹具中的 `scenario/research` 夹具数据假设仍作为独立债务保留，本次没有删除或放宽它。

后续资源商店改动必须继续通过共享页面 seam；不得为某一种商店单独恢复页面级滚动、复制筛选状态，或在详情标题中重新加入与商店 Hero 重复的类型文案。

## 资源详情能力说明与空场景筛选

### 症状与根因

资源详情虽然列出了发布者、兼容宿主和安装事实，但没有先回答“它是什么、能做什么”，用户只能看到内部治理说明。详情容器又使用 Grid 默认的拉伸对齐，把少量内容行扩展到剩余视口高度，造成大块空白。Skill 商店还在无有效场景数据时渲染一张“当前目录尚未提供可用的场景分类”空卡，增加了噪声。

## 深色主题一致性与装饰标签降噪

- 根因是 `CreatePolygonRgn` 与 `SetWindowRgn` 只能生成二值 Windows 区域，没有每像素 alpha 和抗锯齿。增加多边形顶点只会改变阶梯密度，无法得到平滑曲线；同时把整个 620 × 620 窗口裁成细长四角星后，标准 NSIS 控件没有稳定的矩形可用区域。
- 星形源资产现已追溯到本机 Codex 对话 `设计枕星AI商店LOGO`（thread `01a00b45-6be0-7190-b081-5aa539c5e749`）。对话从“枕星AI商店”原创提示逐步收敛到单颗、纯灰、透明背景的四角星，没有引用 Gemini、Google 或第三方素材；生成记录闭合了来源链，但不替代商标近似复核。

### 最小修复与防回退

- 移除 `CreatePolygonRgn`、`SetWindowRgn` 和手工区域内存；主窗口改用透明色键 layered window。星体继续以抗锯齿位图呈现，不再用窗口区域描边。
- 星体保持为上半部的主视觉；标题、说明、安装位置、进度和三个操作按钮统一收进下半部独立的半透明深色控制区，避免任何控件穿过星形轮廓。
- 安装与卸载仍复用同一 8 级灰到银进度和同等级呼吸高光；本次只纠正窗口承载和布局，不改变全机安装、目录选择、进度映射或反向卸载语义。
- 品牌合同新增反回退门禁：禁止重新出现 polygon region；要求 layered color-key；要求标题、目录、进度和按钮全部位于控制区的固定安全范围。
- 真实 RED 精确命中旧 `CreatePolygonRgn`；最小实现后品牌合同 3/3 GREEN。生成的静态首帧与银色完成帧均显示平滑星体和完整控制区。
