# 本地证书轮换与安装点击无反馈

日期：2026-08-02

## 用户可见问题

- 已下载的 OpenClaw Windows Hub 安装包点击“立即安装”后没有可见响应。
- 厂商安装器启动较慢时，按钮仍保持可点击，用户无法判断是否已受理。
- 安装器最终启动并完成安装，但旧客户端没有及时展示已安装状态。

## 证据

- 0.1.25 包内固定的 localhost 叶证书指纹为 `4B:36:73:DC:...:0F:B1`，该证书已过期。
- Caddy `tls internal` 已自动签发新叶证书，当前指纹为 `C1:76:C9:94:...:BF:D8`。
- 旧客户端拒绝新叶证书后只能读取缓存目录；安装安全策略按设计拒绝用缓存授权新的本地执行。
- `installer:launch` 在确认窗口、操作状态登记和进程启动之前返回 `ACTIVE_CATALOG_UNAVAILABLE`。
- 安装失败写入 `productErrors[productId]`，安装包管理卡片却只显示 `managementMessages[packageId]`，因此错误被隐藏。
- OpenClaw 0.6.12 已在本机完成安装：注册表、安装目录、主程序 Authenticode 签名和交互式卸载器均符合现有白名单。
- 厂商安装器解压约 372 MB，并等待 VC++ 运行库提权；用户确认后运行库以退出码 0 完成。
- OpenClaw 安装完成后，发布验收仍在产品检测结束前点击短暂出现的“安装”按钮；真实逻辑随即切换为“已安装”，因此不会创建下载任务，验收等待 30 秒后回滚。

## 根因

本地发布客户端固定了短命的 Caddy 叶证书，而不是稳定的本地根 CA。叶证书正常轮换后，已发布客户端无法继续建立受信的本地 HTTPS 连接。与此同时，安装包管理页没有复用产品安装阶段和产品错误状态，掩盖了真实失败，也没有覆盖安装器解压与运行库准备期间的等待体验。

发布验收还假设目标桌面产品始终未安装，未按真实设备检测结果区分“首次安装”和“获取最新版”，形成了依赖检测时序的竞态。

## 被否定的假设

- 不是 OpenClaw 安装包损坏：大小、SHA-256 和签名均已通过审核策略。
- 不是 Clash 专属问题：失败发生在客户端自定义 localhost 证书校验层。
- 不是需要给 OpenClaw 增加新的识别特例：当前官方安装记录已满足通用桌面产品适配器。
- 不能通过允许缓存目录授权安装来绕过，因为这会破坏后台启停和撤销策略的安全边界。

## 修复

- 本地发布信任改为固定持久化 Caddy internal 根 CA，允许同一根 CA 下的 localhost 叶证书正常轮换；错误主机、错误根和无效证书仍被拒绝。
- localhost 校验失败时直接拒绝，不交回系统信任链兜底；只有固定链遇到未知根错误时由客户端放行，公共网站仍交由 Chromium 正常校验。
- 安装包管理卡片复用现有产品阶段和错误状态：请求受理后立即禁用按钮并显示简短等待文案，失败直接显示在对应卡片。
- 本地发布打包器关闭旧 Portable 时同时追踪并关闭其 Electron 子进程，避免父进程退出后残留临时目录子进程阻塞真实验收与回滚。
- 发布验收先读取桌面产品安装状态：未安装时点击“安装”，已安装时点击“获取最新版”；两条路径都必须通过真实渲染器按钮进入同一个灰色忙碌状态。
- DOM 验收动作白名单同时纳入通用的 `refresh-product`，避免状态选择正确后又在点击助手入口被拒绝。
- 保留“必须由新鲜远程目录授权本地执行”的既有安全边界。

## 验证

- 已完成：真实 Caddy 根证书写入成功；叶证书轮换、错误根、错误主机、过期证书和运行时覆盖层针对性检查通过。
- 已完成：安装包卡片等待态与错误展示针对性检查通过。
- 已完成：已安装与未安装两种桌面产品下载入口的状态选择回归检查通过。
- 已完成：全量单元测试与 TypeScript 检查通过。
- 待完成：新 Portable 在真实 Windows 上刷新目录、识别 OpenClaw、打开和卸载入口验收。

## 剩余用户验收

新版本需在当前 Windows 用户账户下确认：打开 AI Hub 后 OpenClaw 显示为已安装，按钮操作期间有明确状态，厂商程序能打开，卸载仍保留厂商交互界面。

## 预防门禁

- 本地发布包不得固定短命叶证书。
- 发布测试必须覆盖同根 CA 叶证书轮换，并拒绝其他根 CA。
- 安装入口的异步请求必须在同一卡片展示忙碌状态和错误。
- 发布验收不得假设设备未安装目标产品，必须从真实检测状态选择对应入口。

## 2026-08-05：0.1.41 v2 目录恢复场景的假 TLS 失败

### 用户可见问题

- `scenario-b-cdp` 记录到同一 0.1.41 Portable 首次从 v2 远程目录读取 375 个厂商、615 个产品；上游 4173 停止时 4443 实际返回 502，客户端安全保留 `source=cache`。
- 上游恢复为 200 后，测试立即以同一隔离 profile 重启 Portable，报告却仍为 `source=cache` 并显示 `net::ERR_CERT_AUTHORITY_INVALID`，没有回到 `remote`。

### 证据与根因

- 该 Portable 的本地证书回调实际收到 `net::ERR_CERT_AUTHORITY_INVALID` 后，对 `localhost` 的固定 Caddy 根链均记录 `accepted:true`；当前 4443 根指纹也与包的 `local-release-trust.json` 一致。因此不是缺少 `--ignore-certificate-errors`、不是根证书轮换，也不应以放宽 Chromium 证书校验修复。
- `scripts/lib/packaged-client-cdp.mjs` 的 `close()` 在按隔离 `--user-data-dir` 停止进程后只固定等待 250ms，未等待 Portable 子进程和该 profile 的网络会话完全退出。立即重启可稳定复现上述缓存/TLS 表象；相同包、相同 profile 仅将退出后等待改为 5 秒，两次启动均为 `remote`、v2=1、375/615。
- 这不是旧 HTTP 连接的持久复用：客户端每次 `catalog:get` 都以 `cache: "no-store"` 请求远程目录，启动时还关闭默认 session 的连接；失败由未完成的前次 Portable 生命周期与同 profile 的过早重启触发。
- 缓存策略按预期工作：`resolveCatalog()` 先读取已验签同频道缓存、仍尝试远程；只有远程请求抛错才返回 `cache`。它保留目录是安全回退，不是 TLS 或恢复失败的原因。

### 修复与验收门禁

- CDP/Portable 验收 harness 必须在同 profile 重启前轮询确认所有带该 `--user-data-dir` 的进程已退出，并确认该 profile 不再被占用；不得以固定 250ms 延迟替代退出屏障。
- 场景报告必须保留 `local-release-certificate.log`，同时断言固定链回调为 `accepted:true` 与恢复后的 `catalog:get` 为 `source=remote`。只断言渲染错误文案不能区分 TLS 信任失败和测试生命周期竞态。
- 回归顺序：远程预热为 `remote` → 停 4173 后确认 4443=502 且客户端为 `cache` → 恢复 4173/4443=200 → 等待旧 Portable 完全退出后同 profile 重启，必须恢复 `remote`。不得把 `--ignore-certificate-errors` 加入验收命令。
