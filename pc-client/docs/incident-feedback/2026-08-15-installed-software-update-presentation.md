# 已安装软件与运行环境更新呈现

## 现象

- 环境管理把 Python 3.12 和 Python 3.13 当成两个并列产品：3.12 显示已安装，3.13 显示未安装。
- “已安装的产品”又把未安装的 Python 3.13 放进“可重新安装”，让未安装项看起来像本机已有软件。
- 桌面软件虽然已经能从受信任的 Windows 软件包清单取得 `availableVersion`，已安装管理模型却没有把它呈现为用户可选择的更新。
- Skill、MCP 和插件已有本地收据、过期状态与显式 `update` 动作，不应另造第二套更新机制。

## 根因

环境扫描同时承担依赖判定与界面展示。依赖判定必须保留 `python` 与 `python312` 两个精确能力 ID，但界面直接渲染原始扫描结果，因而把同一 Python 家族错误地显示成两款软件。已安装管理还把所有 `absent` 环境视为可重新安装，没有先证明它曾经安装。

桌面产品状态已经包含软件包管理器提供的新版本字段，但投影层只保留当前版本、位置和卸载能力，导致更新事实在到达界面前丢失。

## 修复

- 保留原始 `checks` 供产品依赖判断，新增只用于界面的 `displayChecks`。
- Python 家族只显示一张卡：优先显示已安装成员；仅安装 3.12 且审核推荐为 3.13 时，在 3.12 卡片显示“有更新”，更新目标固定为 `python`。
- 更新准备和打开安装包时由主进程重新扫描 Python 家族成员，不能信任渲染层传入的当前版本。
- 未安装环境不再进入“已安装/可重新安装”；缓存安装包仍留在安装包管理区，不冒充已安装产品。
- 桌面软件只有在有效的本地批准 profile、启用目录能力和软件包管理器 `availableVersion` 同时成立时才显示“有更新”。点击后只进入既有受审更新入口；不会后台自动升级。
- Skill、MCP 和插件继续使用既有 `outdated` 状态及收据约束下的显式更新动作。

## 验证

- TDD 首轮精确失败：缺少 Python 家族投影、跨小版本更新基线、未安装环境过滤和桌面更新投影，共 4 个失败。
- UI 首轮精确失败：设置页未消费家族卡片，桌面卡没有显式更新动作，共 2 个失败。
- 修复后相关 focused tests 全部通过。
- TypeScript/Vite build 与 lint 通过；仅保留既有浏览器 externalization 和大 chunk 警告。

## 安全边界

- 不自动安装，不在扫描时启动安装器；用户必须点击更新。
- Microsoft Store 或厂商自更新的软件仍由其原更新所有者负责；没有可信新版本事实时只显示更新归属，不伪造“有更新”。
- 目录中的未安装 Skill/MCP/插件、仅链接资源和 discovery-only 资源不进入已安装更新列表。
- 本次不改变 catalog、发布通道、签名、服务端或安装包；真实 Windows 打包验收仍需后续单独执行。

## 预防门

新增任何更新入口必须同时证明：本机已安装身份、可信当前版本、可信目标版本、更新所有者、用户显式确认和更新后重新检测。依赖能力 ID 可以按版本拆分，但面向用户的产品卡必须按软件家族去重。

## 2026-08-15：统一软件更新中心与后续资源自动纳管

### 新现象与证据

- 客户端虽然能本地检测部分运行环境、桌面软件、CLI 和扩展的新版本，但“检测”本身会直接决定按钮是否出现，后台没有统一审核与发布控制面。
- Windows 软件包管理器已经能执行受审 `upgrade`，旧“获取最新版”按钮却只打开厂商网页；Skill、MCP 和插件也没有与桌面软件共用发布许可。
- 后续新增厂商或产品若只修改目录页面，不会自动进入任何更新审核清单，容易再次出现逐产品补按钮的特例。
- 用户要求的行为是：客户端启动后自动读取后台已经发布的更新；用户只负责选择单项“立即更新”或“全部更新”，不再先点击“检测更新”。

### 根因及排除项

根因是“本机版本检测”“允许向用户展示的更新”和“执行更新”三个职责没有独立建模。仅把按钮文字改成“立即更新”不能建立后台发布许可；把任意下载地址、命令或凭据放进网络清单又会绕过客户端现有受审适配器，因此也被排除。厂商自己的自动更新器仍由厂商负责，不能伪装成 AI Hub 受管更新。

### 统一修复

- 新增独立的 `software-updates` 签名发布类型。网络清单只允许固定 `{kind, subjectId, mode, version}`，不接受 URL、命令、参数、环境变量、凭据或安装配置；客户端继续只执行本地审核过的下载、包管理器、CLI 或扩展适配器。
- 后台新增“软件更新中心”，流程固定为“检测全部软件 → 审核选择 → 一键签名发布”。扫描统一枚举环境下载注册表、产品安装注册表、Skill/MCP/插件安装注册表和当前目录产品。
- 后续注册到上述共享模块的环境、产品和扩展会自动进入更新清单；仅出现在目录中的新产品也会自动进入 `manual-review`，在补齐受测客户端适配器与可信版本前不能发布。
- 客户端启动时自动验签并读取软件更新发布，不启动安装动作。只有同时满足“后台签名发布 + 本地已安装证据 + 本地适配器可更新”的项目才显示“立即更新”。
- “全部更新”只汇总这些已经通过同一门禁的已安装项目，并按现有安全路径逐项执行；环境更新仍先进入下载模块，第三方安装器仍需用户确认，不把打开安装器当成更新完成。
- 管理员可发布空清单来撤回全部旧更新；发布版本仍递增，客户端用高水位记录拒绝回退或同版本换内容。
- 四套 Caddy 部署拓扑只新增固定 `/software-update-release.json` 反向代理；社区 Apache 后端不承担该签名发布职责。

### 自动验证

- TDD 首轮精确失败覆盖：缺少软件更新发布模块、未来目录产品未纳管、后台接口/UI 不存在、客户端未启动自动检测、无单项/全部更新入口。
- 撤回场景的追加 RED 同时在协议验证和后台发布处失败；允许零条目的签名清单后 GREEN。
- 软件更新协议、后台状态机、服务端接线、客户端接线、部署路由、已安装产品、扩展 IPC、环境更新、Windows 包管理器和语言模块相关测试最终 55/55 通过。
- 真实 Electron 隐藏窗口在 1365px 与 740px 两种宽度均渲染“后台已发布 1 项软件更新”“全部更新（1）”和单项“立即更新”；所有可见按钮均在视口内。该夹具不连接真实发布服务，也不执行下载或安装。
- TypeScript/Vite build 与 lint 通过；构建只出现既有 Node 浏览器 externalization 与大 chunk 警告。

### 剩余人工验收与防复发门禁

- 本轮没有启动后台、签名或发布真实软件更新，也没有封包、安装新客户端、调用包管理器或第三方安装器；真实 Windows 验收和服务器部署必须在后续授权下单独执行。
- 新增厂商不等于自动获得更新权限。新软件必须进入共享注册表或目录扫描；目录-only 项必须保持 `manual-review`，直到固定身份、版本来源、更新所有者、本地适配器和更新后复检全部闭合。
- 任一客户端更新执行入口都必须重新核对当前已验签发布；前端状态、旧缓存或目录能力不能单独授权更新。
- 发布空清单是撤回路径，必须保留测试；不得通过“至少一项”按钮限制让旧发布无法撤回。

## 2026-08-15：真实 Windows 识别、下载、撤回与 0.1.97 验收

### 真实故障与修复

- 本地后台已经发布 Python 更新，但真实客户端仍显示“全部更新（0）”。直接扫描发现 Node.js、Git、Python、Docker 和 WSL 的注册表版本存在，却统一得到 `installed=false` 与 `detection=unknown`。
- 根因是 Electron 继承了 PowerShell 7 的 `PSModulePath`，再启动 Windows PowerShell 5.1 时无法加载 `Get-AuthenticodeSignature` 所需模块。该失败让已安装检测误降级，不是发布清单或版本比较错误。
- 新增 `windowsPowerShellEnvironment()`：启动 Windows PowerShell 5.1 前仅移除继承的 `PSModulePath`，其余隔离环境保持不变。专属测试先以缺失导出得到 RED，修复后 3/3 GREEN。
- 预防门禁：任何调用 Windows PowerShell 5.1 的签名或注册表检测路径，都必须使用该统一环境清理函数；不能让调用点各自修补，也不能把检测异常解释为“未安装”。

### 真实链路验收

- 修复后的真实 Electron 扫描正确识别 Node.js 25.2.1、Git 2.55.0.4、Python 3.12、Docker 4.83.0 与 WSL 2.7.10.0；Python 家族卡显示目标 3.13.14 和“全部更新（1）”。
- 用户触发“全部更新”后，下载模块完成 `python-3.13.14-amd64.exe` 的 29,225,624 字节下载；第三方安装器没有自动启动，仍由用户决定何时安装。
- 管理端随后发布空的签名清单，客户端刷新后显示“当前软件均为最新版本”和“全部更新（0）”，证明撤回不会继续暴露旧更新。
- focused 59/59、根项目与客户端 build、lint、布局夹具均通过。0.1.97 review 包仅执行一次并安装到本机，已安装版本与可执行文件版本均为 0.1.97。

### 尚未越过的边界

- 0.1.97 是本地未签名 review 包，不是正式签名发布。
- 截至该轮验收，生产地址对 `/software-update-release.json` 返回 404。社区 Apache 不负责该签名清单；该缺口已在下述 2026-08-16 生产切片闭合。
- 本次验收下载的 Python 安装包保留在用户下载目录，未静默安装或删除。

## 2026-08-16：生产软件更新清单上线

### 生产故障与最小修复

- 上线前反馈回路为：`/software-update-release.json` 返回 404，而 `/channels/v2/catalog-release.json` 与社区首页均返回 200。DNS 和直连源站复核证明请求已到 `47.236.62.189` 的生产 Caddy，不是 Sites、Apache 或客户端缓存问题。
- 生产 Caddy 仍使用旧热修配置，生产 Admin 镜像也没有软件更新接口；直接升级整套 Admin 会无谓扩大到社区与身份服务。
- 生产拓扑改为由 Caddy 从现有 Admin published 目录只读提供固定文件。网络仍只能获得已签名的 `{kind, subjectId, mode, version}` 发布清单，不获得下载地址、命令、凭据或安装配置。
- 基础 Compose 增加 published 目录只读挂载；独立 hotfix overlay 只替换受审 Caddyfile 并加入同一只读挂载，便于旧生产 release 在不重建其他服务的情况下采用修复。

### 部署与反馈回路

- 部署前清单使用客户端同一公钥链验签通过：`releaseVersion=2`、`entries=0`、429 字节、文件 SHA-256 `8a9628eddc35424639e7b63a4792838df352158755c26ebed334e256e153ca99`。
- 新 Caddyfile 与线上旧文件逐行对比，唯一语义差异是新增固定软件更新路径；使用线上当前 Caddy 镜像 ID 离线校验得到 `Valid configuration`。
- 仅执行一次 `docker compose ... up -d --no-deps --force-recreate caddy`。Admin、Identity、社区、PostgreSQL 与 MariaDB 的容器 ID 和启动时间均未改变，部署后六个服务全部 healthy。
- 生产 GET 最终返回 200、`application/json`、`Cache-Control: public, max-age=0, must-revalidate`；响应仍为 429 字节且 SHA-256 与发布源一致，客户端同款验签再次通过。目录、社区与健康接口继续返回 200。
- 本轮没有改 Apache、数据库、社区数据、身份数据或密钥，没有运行安装器，也没有给空清单伪造更新。客户端下次启动或刷新时会自动读取这份已发布撤回态。

### 验证边界与预防门

- 专属部署测试先因生产缺少只读静态路由与挂载得到 RED，修复后 2/2 GREEN；软件更新协议、服务端接线和部署相关用例通过。
- 较大的 community production 套件另有两项既有 Identity source-manifest 漂移，与本次 Caddy 文件和软件更新路由无因果关系；本次没有借机修改 Identity 构建闭包。
- 以后新增更新类型仍必须先由软件更新中心检测、管理员审核并签名发布；生产只暴露固定签名清单，客户端再以本地受审适配器执行用户明确选择的单项或全部更新。
