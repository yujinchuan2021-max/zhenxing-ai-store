# 厂商 Logo 错配与低对比

- 日期：2026-08-03
- 影响：全部 AI 厂商、全部 AI 可接入厂商、搜索结果和资源商店中的厂商标识

## 现象与证据

- Cline 与 01.AI 显示成不同底色的 GitHub Octocat；继续检查发现 LangChain、LostRuins、Open WebUI、ThinkInAI 也共享同一文件哈希。
- AMD、Block、Intel 和金山办公使用了各自官方站点图片，但前端仍把图片放在 `vendor.color` 色块上，造成黑底黑标、蓝底蓝标或红底红标；AMD 的旧 favicon 还只有 16×16。
- 红灯命令 `node --test tests/vendor-logo.test.cjs` 同时捕获“图片仍使用厂商色底”和“一个 Logo 资产关联七个厂商”两项失败。

## 根因

1. 旧导入逻辑把厂商的 GitHub 仓库页当作官网，从页面读取到 GitHub 自身 favicon；内容寻址存储又按相同文件哈希合并来源，于是错误 Octocat 被多个厂商共用。
2. 后续导入器已经改成审核来源优先，但只处理没有 `iconAsset` 的厂商，历史错图没有进入重审队列。
3. 原测试只验证图片文件、哈希、HTTPS 来源和厂商 ID 包含关系，没有验证品牌身份，也没有禁止不同厂商共享同一图标。
4. `VendorMark` 无论显示图片还是文字回退，都统一使用 `vendor.color` 作为背景，未考虑透明 Logo 的对比度。

## 排除的错误判断

- 不是目录发布主机或图片解码失败：截图中的图片能够稳定显示，错误发生在图片身份和视觉组合。
- 不是六个厂商都缺少官方图片：AMD、Block、Intel 与 WPS 的来源属于官方域名，主要问题是渲染底色；Cline 与 01.AI 才是实际错图。
- 不能给 LostRuins 换成 GitHub 个人头像：个人头像不等同于项目或厂商品牌。

## 修复

- 图片型厂商 Logo 使用白色中性背景并占满容器；文字回退继续使用厂商颜色，避免品牌图片被二次缩小。
- AMD、Cline、LangChain、Open WebUI、ThinkInAI 改用各自官方 GitHub 组织头像；Intel 保留官方 favicon，但由白底保证可读性。
- 01.AI 的官方组织横向字标在 36px 卡片中仍不可读，而且官方品牌条款要求事先书面许可，改用审核文字回退，不再分发图形 Logo。
- AWS、Redis、Stability AI、NVIDIA、Nous Research、Supabase、Ableton、UiPath 和 Open Home Foundation 的历史错配、精灵图或低质量资产完成第二轮替换。
- GitHub favicon 只保留给 GitHub；LostRuins 改用审核文字回退。
- 导入器拒绝把 GitHub 通用 favicon 分配给其他厂商，清理共享资产，并按当前目录重建来源清单的厂商关联。
- 回归测试禁止一个 Logo 内容哈希归属多个厂商，并固定图片型 Logo 的中性底规则。
- 已审核文字回退成为导入器的显式阻断清单；导入器不再反复抓取这些厂商的 favicon，只有先完成人工品牌复核并移出清单才能升级为图片。

## 验证与防复发

- 聚焦测试：`node --test tests/vendor-logo.test.cjs`。
- 最终自动巡检覆盖 183 个厂商、128 个当前图形资产和 55 个审核文字回退；当前 128 个引用全部成功解码。历史签名目录仍引用的内容寻址文件继续保留，不能按“当前目录未引用”直接删除。
- 本轮曾在新目录发布前删除旧 Logo，导致旧草稿就绪检查报告资产不存在；统一发布 v48 后恢复。新增回归测试遍历全部历史签名目录，确保每个 Logo URL 的文件和 SHA-256 仍可验证。
- 发布前继续执行目录校验、完整发布测试、生产构建和真实页面验收；浏览器要分别检查错图厂商、透明深色 Logo 和文字回退。
- 新增 Logo 不能只看下载成功或哈希正确；必须保存品牌所有者证据，并检查最终卡片的实际视觉结果。
- 后台 Logo 更新仍通过目录发布完成，不需要为纯目录图片变化重新封装客户端；本次同时修改了前端背景规则，交付客户端时再随下一版封包。
