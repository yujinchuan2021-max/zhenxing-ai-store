# 用户验收后代码审计整改

## 范围

用户确认托管下载与安装器调起后，针对目录刷新、本机产品管理、CLI 生命周期、下载网络、产品审批、语言边界和发布可追溯性进行了完整代码审计。

## 发现的问题

- 打包产物未强制绑定固定源码提交，旧包与新源码容易混淆。
- CLI 产品存在按产品分支实现，新增产品时容易漏掉安装、检测、打开、更新或卸载能力。
- 部分受管制品下载没有经过统一的系统网络、重连和重试通道。
- 客户端可能对每个桌面产品重复扫描系统，启动时还会提前执行环境扫描。
- 后台下架产品后，本机已安装产品可能从管理页消失。
- 产品执行档案缺少独立审批记录，运行时文案与系统错误也没有统一收口。
- 分类仍有前端硬编码，文档中的发布顺序和候选版本已经过时。
- 干净副本安装依赖时发现发布工具链锁定了存在拒绝服务漏洞的 `brace-expansion` 版本。
- 干净副本还暴露出单测读取被忽略的本地运行目录、Vite 误继承仓库根 PostCSS 配置的问题。
- Docker 健康切换后曾出现宿主机端口映射仍指向旧 Caddy 连接的问题；原证书固定脚本只尝试一次。
- 首次切换到 schema v2 时，旧 schema v1 当前目录无法通过新验证器，也就无法按旧逻辑先归档再替换。

## 整改

- 所有 CLI 驱动统一注册并通过同一生命周期分发器执行。
- 所有托管安装制品统一使用独立 Electron 下载会话，重新读取 Windows 当前系统网络并进行有界重试。
- 本机产品管理改为一次批量扫描，并将后台目录与本地已发现库存合并。
- 产品执行契约使用哈希与独立显式审批绑定；后台只能选择客户端已批准策略。
- 运行时提示统一进入中英文语言模块，渲染边界不再直接展示底层异常。
- 发布包记录版本、Git 提交、工作区状态、制品大小与 SHA-256；生产发布拒绝脏源码并要求同版本标签。
- 隔离打包客户端必须验证远程签名目录、同版本更新、扩展安装/卸载，并真实下载至少 1 MiB 后暂停。
- 锁文件中的 `brace-expansion` 已提升到修复版本，发布前 `npm audit` 必须为零已知漏洞。
- 发布策略单测改用自包含签名通道夹具；PC 客户端使用自己的空 PostCSS 配置，不再依赖父项目安装状态。
- 一键发布会先重建 HTTPS 发布容器以刷新端口映射；证书固定读取再使用最多六次、指数退避且总量受限的重试模块，证书身份仍按 localhost、Caddy CA 与 SHA-256 指纹严格校验。
- 本地发布只有在显式迁移模式下，且旧目录通过 schema v1 的清单、签名、文件哈希和通道一致性完整校验后，才会隔离旧目录；损坏的 v2 仍直接拒绝。新目录最终校验失败会原位恢复旧目录，提交后的旧目录清理失败只记录为可重试清理，不把已成功切换误报为失败。
- 发布运行目录、staging 根和关键子目录拒绝符号链接与 junction，并用真实路径约束在可信根内，避免把运行目录外的内容激活为 current。
- 运行目录本身会先校验再创建 `backups` 与 `staging`，拒绝 runtime junction 时不会先向 junction 目标写入；发布切换和手动备份共用跨进程互斥锁，竞争进程不能删除另一进程的 current。
- 互斥锁携带进程、时间和随机所有权令牌；持有进程退出后可原子隔离并恢复 stale lock，正常退出也会重试清理。锁目录删除失败只返回 pending，不会覆盖已经成功的发布结果或原始失败。
- runtime 创建前会逐级拒绝父路径中的 symlink/junction，父级跳转到工作区外时保持零创建；锁目录尚未写入 owner 或 owner 损坏时，初始化宽限期内拒绝抢锁，宽限期后才原子隔离并恢复，覆盖进程在两步之间崩溃的窗口。
- v1/v2 共用同一套清单、通道、签名与文件树验证骨架；v1 明确拒绝 provenance 等未声明残留文件。staged 与 current 不再各重复三次大文件哈希，正常同卷切换只保留切换前后两次完整校验。
- 普通 v2 备份、legacy retired 目录和跨卷 staging 的清理失败均作为可重试清理状态返回，不会把已经验证并激活的新 current 误报为发布失败。
- 跨卷复制和手动备份复制若中途失败，会只清理由本事务创建的残缺目标，再恢复旧 current；不会留下阻断回滚的 partial 目录。
- staging 和生产发布包仍严格拒绝额外客户端配置；仅已激活的本地 current/backup 可携带 `local-release-trust.json` 运行时覆盖层，且必须通过 origin、指纹和有效期校验。备份恢复时先移除该覆盖层，再由 TLS 固定步骤生成当前证书配置。
- `runtime/current` 原子替换后会再次强制重建 release-server，使 Docker Desktop 明确重新挂载当前目录实体，再执行 HTTPS 文件与来源证明验收。
- 本地 Caddy 文件白名单明确包含签名 `build-provenance.json`，并与总清单同样使用 `no-store`；未知文件继续返回 404。

## 验收边界

自动化不会启动第三方安装器。最终仍由用户在日常 Windows 账户中确认 Setup 安装、第三方安装向导、安装后探针和卸载交互。
