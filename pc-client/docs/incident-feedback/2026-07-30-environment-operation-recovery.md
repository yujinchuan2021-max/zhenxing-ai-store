# 环境安装器的持久恢复与安全门禁

## 事故范围

Python、Node.js、Git 等环境安装已经具备“客户端下载固定安装包、用户再次点击后打开安装程序”的基本流程，但仍出现了几类会误导用户的问题：

- 页面刷新、窗口关闭或客户端重启后，“正在打开安装程序”“正在确认安装/卸载”的页面状态会丢失，用户可能重复启动同一个安装器或卸载器。
- 安装程序被 Windows 接收不等于安装成功；卸载程序被打开也不等于软件已经移除。
- 已安装旧版本时再次打开安装包，安装器会显示 Upgrade。若客户端没有记录安装前基线，现存的旧版本证据会被立即误判成这次安装完成。
- `PATH` 尚未刷新、注册表扫描暂时失败或厂商注册表字段与预期不同，都可能把“未知”错误降级成“未安装”。
- 下载镜像的探测结果与真实下载响应可能不同，不能因为用户位于国内或配置了 Clash 就跳过官方源。

这些问题不是按钮文案问题，而是状态所有权、可信证据和恢复协议不完整。

## 为什么页面状态不够

React 页面只能表达当前窗口看到的状态，不能拥有本机安装生命周期：

1. 页面刷新会清空组件状态和定时器，但外部安装器或卸载器可能仍在运行。
2. 页面关闭后无法继续扫描 Windows 注册表和真实可执行文件。
3. 旧页面的迟到 Promise、下载事件或检测结果可能覆盖新操作。
4. 页面无法证明主进程是否已经创建外部进程，也不能安全决定是否再次创建。
5. “按钮已点击”“进程已打开”和“环境已安装”是三个不同事实，不能合并为一个布尔值。

因此页面只负责展示主进程快照和发起带身份的手动检测；下载来源、安装器启动、持久操作、Windows 证据和卸载动作都由主进程负责。

## 主进程持久操作协议

环境安装与卸载复用统一的两阶段操作控制器，但使用独立的 `environment-operations.json`：

```text
begin -> launching -> monitoring -> installed / uninstalled
                            \-----> timed-out
```

- 每个环境同一时刻只允许一个安装或卸载操作。
- `generation` 在该环境每次新操作时单调递增；系统时钟回拨不能让旧操作重新变新。
- `operationId` 是一次操作的随机身份；手动检测必须同时携带 `generation + operationId`。
- `revision` 只在同一操作身份内递增；页面按 `generation + operationId + revision` 拒绝迟到快照。
- 用户确认且安装包或卸载动作完成最终复核后，主进程先原子写入 `launching / pending`，写盘成功后才创建外部进程。
- 收到进程 `spawn` 后写入 `monitoring / confirmed`；若客户端在创建进程附近退出，重启把持久的 `launching` 恢复为 `monitoring / unknown`，只恢复检测，不重新启动第三方程序。
- 安装、卸载、页面刷新和客户端重启都沿用原始身份与截止时间；超时后保留“立即检测”，不伪造终态。
- 写盘失败时保留最后一个已落盘快照，并对 `launching -> monitoring` 提交和启动失败后的 tombstone 清理做身份绑定的定时重试；重试只提交状态或清理同一操作，不会再次创建外部进程，也不会错误开始监控。
- 终态只保留该环境的 generation tombstone，防止上一代迟到结果覆盖下一代操作。

## 下载源与镜像门禁

- 安装包版本、文件名、官方 URL、可信镜像 URL 和允许的最终主机名固定在客户端白名单中，不接受页面或 CMS 下发任意可执行地址。
- 所有地区都先探测并尝试官方源；只有官方源探测失败、真实下载失败或连续无进度时，才继续尝试对应的可信镜像。
- Clash 或本地代理只影响同一下载通道的联网方式，不改变“官方优先”的顺序。
- 探测与下载必须使用同一 Electron 网络通道；最终重定向仍须为 HTTPS 且主机位于该来源白名单。
- 响应必须满足允许的下载状态和内容条件。曾使用的 TUNA Python 镜像在真实请求中返回 `403`，不能继续当作可用源，因此从白名单移除并替换为华为云镜像。
- 当前 Python 可信镜像固定为 `mirrors.huaweicloud.com`；它仍只是官方源失败后的后备项。
- 下载完成后验证 SHA-256、Authenticode 和固定签名者；用户第二次明确点击前不会自动运行安装包。
- Windows 注册表的 `Publisher` 与 Authenticode 证书主体是两类证据，不能共用同一字段或正则。例如 Git 的注册表 Publisher 是 `The Git Development Community`，但当前官方安装器、`git.exe` 和卸载器的有效签名者是 `CN=Johannes Schindelin`。

## Windows 环境证据与三态

环境状态统一为 `installed / absent / unknown`：

- `installed` 必须来自真实存在的可信可执行文件或其他经过审核的安装证据。
- `PATH` 只负责给出候选位置，不能单独证明已安装。候选必须先解析为 canonical path，再通过对应厂商的 Authenticode 签名验证；WindowsApps 别名、同名空壳或签名不匹配的文件均不能成为 `installed` 证据。
- `absent` 只允许在注册表扫描完整成功、可执行文件探测也成功且两类证据都不存在时产生。
- 注册表或可执行文件探测失败、可信注册项仍存在但主程序暂时找不到、路径尚未刷新等情况均为 `unknown`。
- 安装只在可信 `installed` 时完成；卸载只在可信 `absent` 时完成。`unknown` 对两种操作都不是终态。

Node.js 的真实机器基线证明不能硬编码理想注册表字段：

- 当前机器的注册项 `DisplayName` 为 `Node.js`，`Publisher` 为 `Node.js Foundation`，不是只有 `OpenJS Foundation` 一种值。
- 当前机器的 Node.js 25.2.1 MSI 注册项 `InstallLocation` 为空，卸载字段为 `MsiExec.exe /I{产品代码}`。
- 因此发布者白名单同时接受审核过的 `OpenJS Foundation` 与 `Node.js Foundation`；空 `InstallLocation` 不能被拼成虚假路径。
- 有可信且非空的 `InstallLocation` 时，只接受其中真实存在的固定 `node.exe`；路径为空时继续结合 `PATH`、真实文件和注册项证据，不得因为单一字段缺失就报告 `absent`。
- Python 同样不能只依赖 `PATH`；官方 PythonCore 注册表提供的绝对 `ExecutablePath` 必须指向真实 `python.exe` 才可作为安装证据。

## 已安装基线与 Upgrade 防误报

打开安装器前必须先取得一次可信基线：

- 基线为 `installed`：拒绝再次打开同一环境安装包，并明确提示环境已经安装。这样 Upgrade、Repair 或用户取消不会被现存旧版本证据误报成一次新安装成功。
- 基线为 `unknown`：拒绝启动，要求稍后重新检测；不能带着不确定基线开始自动确认。
- 只有基线为 `absent` 才创建安装操作并打开安装器。
- 安装完成必须观察到该操作之后的可信 `installed` 证据；不能用安装器退出码、按钮点击或窗口出现作为成功依据。

## 安全卸载

- 只有客户端固定白名单中的环境才提供卸载。
- 注册表扫描必须完整成功；候选必须匹配固定显示名、审核过的 Publisher、安装位置或 MSI 产品身份，并且只能收敛出唯一动作。
- 用户确认前先展示环境、版本和卸载信息；确认后重新扫描并重新推导动作，防止确认窗口期间注册表内容被替换。
- Node.js 只接受机器级 MSI 产品代码，并使用固定的 `%SystemRoot%\System32\msiexec.exe /x {产品代码}`，不执行注册表提供的任意命令行。
- Git、Python 和 Docker 只接受各自固定卸载器文件名、固定参数以及预期 Authenticode 签发者；不使用 Shell，不接受额外参数。
- 卸载操作同样先持久化再创建进程；打开卸载器后持续检测，只有完整扫描得到 `absent` 才显示“已卸载”。
- 多候选、扫描不完整、文件不存在、签名不匹配或确认前后动作变化时一律拒绝执行。

## 下载恢复边界

- 已完整下载的环境安装包会保存受控记录。客户端重启后会重新检查文件存在性、SHA-256、Authenticode 和发布者；验证通过才恢复“打开安装包”入口。
- 损坏、缺失或记录不匹配的完成包不会恢复为可执行状态。
- 下载任务会保存精确的受信来源、目标文件、已接收字节数和任务代次；客户端重启后，未完成任务恢复为暂停状态并保留 `.part` 文件。
- 用户继续下载时使用同一个受信来源发起 Range 请求；服务端忽略 Range 或返回区间不匹配时，安全地从零重新下载，避免拼接损坏文件。
- 有可复用部分文件时不切换镜像；只有当前来源在零字节阶段失败，才按“官方源优先、镜像源随后”的批准顺序尝试下一个来源。
- 设置中的统一下载任务列表展示桌面产品与环境安装包的进度、暂停、继续和失败状态；环境行与任务列表都可发起“取消并清除断点”，用户确认后删除部分文件，客户端重启不得恢复已取消任务。
- 完成任务提供“打开安装包、打开所在文件夹、清除记录”：前两项必须重新校验哈希、数字签名和发布者；清除记录需要确认，且只移除 AI Hub 的任务与验证记录，不删除用户电脑上的安装包文件。
- 安装器或卸载器打开后，任务中心用持久化操作身份展示“正在打开、等待完成、立即检测、安装完成或卸载完成”；同一产品的“下载完成”卡片在操作期间隐藏，检测结果同时更新任务中心、厂商产品页和环境检测行。
- 下载完成后仍须重新计算 SHA-256，并验证 Authenticode 与预期发布者，全部通过才恢复“打开安装包”入口。

## CLI 任务中心边界

- CLI 部署和卸载开始后，会立即进入任务中心，并同步展示运行状态、最近 8 条输出日志以及完成、失败或取消结果；结果卡片可由用户手动清除。
- 同一次 CLI 操作的日志和结果与厂商产品页共用状态，任务完成后产品页同步为“已安装”或可重新部署状态。
- CLI 失败或取消后，任务中心直接提供“重试”和“重新检测”：重试会创建新一代操作；重新检测只读取实际安装证据，不重复执行部署或卸载。可信状态满足目标时把原任务收敛为完成，否则保留明确失败结果。
- CLI 任务和日志目前只保存在当前客户端会话中，不跨客户端重启恢复。重启后以实际 CLI 安装证据重新检测，不恢复旧进程、旧任务或旧日志，也不会自动重新执行部署或卸载。
- 客户端启动后会对固定白名单中的 CLI 只执行一次状态读取，更新产品页的实际安装状态与版本；不得因此创建任务、写入运行日志或重新部署/卸载。桥接返回空值或非法三态时必须忽略并允许稍后重试，不能让整个页面崩溃。

## 任务中心筛选与清理

- 任务中心固定分为“进行中、失败、已完成”，默认展示进行中。暂停下载仍属于进行中；超时的桌面/环境检测与失败、取消的 CLI 任务属于失败。
- “清除全部已完成”只在已完成筛选中出现。下载记录由主进程一次确认后逐条安全清理；桌面、环境和 CLI 的已完成展示状态在渲染层同步清除。部分下载清理失败时，成功项消失、失败项保留错误。
- 同一产品的下载、安装、CLI 部署或卸载入口在第一次点击进入异步调用前即取得进程内互斥锁；快速重复点击不能创建第二次桥接调用。主进程仍保留持久化下载及操作身份检查，防止刷新或第二窗口绕过渲染层锁。
- 下载任务恢复会重写并移除损坏、产品不匹配和已下架记录。暂停或失败任务及其经过产品级路径验证的断点同时超过 30 天时，才允许通过既有安全清理函数删除；断点证据异常、扫描失败或本机时钟回拨时一律保留。

## Windows 任务通知

- 下载完成或失败、桌面及环境安装或卸载完成或超时、CLI 部署或卸载完成或失败时，由 Electron 主进程创建 Windows 原生通知。
- 通知使用固定 AppUserModelID `com.aihub.desktop`。下载和持久化操作直接使用主进程可信任务状态；CLI 渲染层只能提交白名单产品、操作、代次和终态，通知标题与内容仍由主进程生成。
- 同一任务身份和终态在当前进程内只通知一次，最多保留 500 个去重键；通知失败只记录错误，不得改变下载、安装或卸载结果。
- 点击产品任务通知只向受隔离渲染层发送固定产品 ID，并返回对应厂商产品页；环境任务返回任务中心。通知不携带或打开任意 URL、命令或文件路径。
- 原生通知冒烟测试只能证明 Windows 通知通道触发了 `show` 事件；用户实际看到通知并点击后正确聚焦窗口，仍属于实机交互验收。

## 系统托盘与退出边界

- 主窗口关闭时，如果系统托盘已成功创建，则只隐藏窗口并继续运行下载、安装检测和通知；托盘创建失败时保持传统关闭退出行为，不能留下用户无法控制的后台进程。
- 托盘提示和菜单首项展示当前活动任务数；点击状态、点击“打开任务中心”，或存在活动任务时单击托盘，都会恢复同一个主窗口并打开任务中心。无活动任务时单击托盘只打开主窗口。
- 托盘同时固定提供“打开 AI Hub”和“完全退出”。重复启动客户端或点击任务通知都会恢复并聚焦同一个主窗口；不会创建第二套任务状态。
- 创建托盘前必须先把持久化中的 `starting/downloading/pausing` 下载状态收敛为安全的暂停状态，避免客户端刚启动时短暂显示一个实际并未运行的下载任务。
- “完全退出”、系统退出或更新退出会先进入 quitting 状态，随后允许窗口真正关闭、销毁托盘并释放桌面及环境操作控制器。
- 托盘图标来自随包发布的 `build/icon.png`，托盘对象由主进程持有，防止被垃圾回收后图标消失。

## 自动化测试门禁

发布前至少覆盖：

- 下载计划：官方源始终第一、官方失败后才镜像、TUNA 不再出现、华为云主机白名单、最终重定向主机校验、下载失败回退和全部来源失败。
- 断点续传：暂停保留部分文件、继续沿用精确来源、客户端重启恢复为暂停、Range 不匹配安全重下、有有效部分文件时不切换来源。
- 取消清理：需要用户确认；活动下载先进入 canceling；部分文件与断点记录清理成功后才进入 canceled；刷新或重启后不得重新显示。
- 完成包恢复：有效文件可恢复；文件缺失、哈希变化、签名无效或发布者不符时拒绝恢复。
- 环境检测：Python 不在 `PATH` 但官方注册表解释器存在；Node/Git 有可信 `InstallLocation`；Node `InstallLocation` 为空；残留路径；注册表扫描失败；可执行探测失败；`PATH` 同名未签名文件不得成为安装证据；`installed / absent / unknown` 三态边界。
- 签名策略：注册表 Publisher 与 Authenticode signer 分离；Git 官方安装包必须接受 `CN=Johannes Schindelin`，不得拿 `The Git Development Community` 去匹配证书主体。
- 操作控制器：启动前原子写盘、generation 递增、revision 单调、operationId 严格匹配、启动确认、重启恢复但不重启外部程序、迟到扫描隔离、时钟回拨、超时后手动检测、写盘失败持续重试。
- 安装基线：已安装和未知状态均不能打开安装器；只有确定未安装才允许开始。
- 启动方式：Node MSI 使用固定 System32 `msiexec`，EXE 直接创建进程且 `shell:false`，立即退出和 spawn 回调异常不会伪造成功。
- 安全卸载：完整扫描、唯一可信候选、确认后复核、MSI 产品代码约束、固定 EXE/参数/签名、`unknown` 不完成、可信 `absent` 才写 tombstone。
- 页面恢复：完成包、安装中、卸载中和超时状态跨刷新保持；同一操作身份不变；迟到下载或旧扫描不能覆盖新操作；页面错误与控制台错误为 0。
- CLI 任务中心：环境检测不得误建部署任务；部署或卸载点击后立即创建对应任务；运行日志、终态、清除动作和厂商产品页状态同步；页面错误与控制台错误为 0。
- 任务筛选与批量清理：三类筛选不串项；每类空态独立；批量清理只调用一次主进程确认；清理后进行中与失败任务保持；同产品快速重复点击只触发一次操作。
- Windows 通知：固定 AppUserModelID；白名单 CLI 通知载荷；任务身份去重；通知失败不改变任务；点击产品通知返回厂商页，点击环境通知打开任务中心；原生通道至少触发一次 `show` 事件。
- 系统托盘：托盘创建、活动任务数和任务中心入口；关闭窗口后窗口隐藏且进程继续；显式退出不得再拦截关闭；打包安装版关闭主窗口后仍保持后台进程。
- 工程检查：环境相关 Node 测试、完整 Node 回归、TypeScript、Vite production build、Electron main/preload 语法检查和 `git diff --check`。

## 实机验收清单

自动化通过后仍需在可删除的 Windows 测试环境完成：

1. 官方源可用时确认不会访问镜像；屏蔽官方源后确认才使用华为云或对应可信镜像。
2. 下载完成后重启 AI Hub，确认恢复的是同一个已验证安装包；下载一半时重启，不把重新下载误称为断点续传。
3. 打开 Python、Node.js 和 Git 安装器后立即刷新页面、关闭窗口并重启客户端，确认操作身份和检测状态恢复，且安装器只启动一次。
4. 对已经安装的 Node.js/Python 点击安装，确认客户端在打开安装器前阻止 Upgrade 假流程。
5. 验证 Node.js 的真实 `Node.js Foundation + 空 InstallLocation + MSI 产品代码` 注册项仍显示为已安装或未知，绝不能显示为确定未安装。
6. 完成安装向导后确认客户端只在可信可执行文件出现时报告成功；取消安装后不得报告成功。
7. 分别取消和完成一次可信卸载向导；取消后保持已安装，完成后等待完整扫描确认 `absent`。
8. 临时制造注册表或 PowerShell 扫描失败，确认界面保持“正在确认/未知”，不显示安装或卸载成功。
9. 在启用 Clash 的实际网络环境重复官方优先与失败回退流程，确认代理不会改变来源顺序。

未经上述实机步骤，自动化结果只能证明协议和受控模拟成立，不能宣称用户机器上的厂商安装、升级或卸载已经完成验收。

## 2026-08-13：全局扫描收敛超时操作与显式更新合同

- 全局环境扫描若取得与当前 timed-out 操作目标一致的可信终态，会用原 `generation + operationId` 把该扫描结果提交一次；身份已变化则拒绝。这样可信 absent 不再被旧 unknown 快照覆盖，也不会删除用户文件。
- 扫描结果新增客户端审核的 `recommendedVersion` 与严格计算的 `canUpdate`。只有 detection 为 installed、安装版本和推荐版本都是纯数字点分版本且安装版本更低时才允许更新；相等、更高、未知、预发布文本和滚动 latest 均不显示更新资格。
- 更新是独立 intent：首次点击只下载或复用客户端固定来源的已验证安装包；再次点击 `openEnvironmentUpdater` 时重新验证旧版本基线、推荐版本、文件哈希与签名后才打开厂商安装器。该路径不创建首次安装操作，也不因旧 installed 基线瞬间报告成功。
- 本轮不自动运行第三方安装器，也不把厂商更新向导退出视为完成。打开后返回 `requiresRecheck=true`，由用户完成或取消向导并重新检测版本；完整的更新操作持久恢复仍待后续协议和真实 Windows 验收。
