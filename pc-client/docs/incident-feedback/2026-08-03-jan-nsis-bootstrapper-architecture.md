# Jan NSIS 引导壳架构误判

日期：2026-08-03

## 现象与证据

客户端完整下载 Jan 0.8.4 后停止任务并返回 `DOWNLOADED_INSTALLER_INVALID`，提示安装包架构或产品身份与客户端白名单不匹配。固定官方文件大小为 57,771,664 bytes，SHA-256 为 `59f2712ff579208c7e50df1d4408675418ca576421998549f787879372ec50b1`，Authenticode 状态为 `Valid`，签名者为 `Jan AI Pte. Ltd.`，`ProductName` 与 `FileDescription` 均为 `Jan`。

最小身份探针进一步确认 PE Machine 为 `0x014c`（x86）。旧合同要求 x64，因此只产生一项 `ARCHITECTURE_MISMATCH`；将预期引导壳架构改为 x86 后，同一文件的身份校验通过。

## 根因

审计时把文件名中的 `x64` 和最终 Jan 应用载荷架构直接当成了安装器可执行文件的 PE 架构。Jan 的 x64 Windows 产物实际使用 x86 NSIS bootstrapper 启动壳，客户端校验的是被启动文件本身，因此旧白名单写错了层级。

## 排除的错误猜测

- 不是下载损坏：文件大小与固定 SHA-256 完全一致。
- 不是签名失效：证书链有效，现有 Jan 签名者规则匹配。
- 不是产品伪装：Windows VersionInfo 中的产品名和文件描述均匹配 Jan。
- 不是网络或镜像切换：失败发生在完整文件落盘后的本地身份校验阶段。

## 修复

- 在统一 Windows 桌面产品白名单与生命周期合同中，把 Jan 下载文件的 PE 引导壳架构改为 `x86`。
- 保留固定 SHA-256、有效 Authenticode、允许主机和 Jan VersionInfo 校验，没有放宽其他安全边界。
- 更新独立审批合同哈希，使旧审批不会继续批准已经变化的执行合同。
- 完整下载重放脚本支持通过 `AIHUB_LOCAL_RELEASE_CLIENT` 指定待验收 Portable，直接验证封装包内合同。

## 自动验证

- 新增秒级回归测试，使用 x86 PE fixture 与真实 Jan VersionInfo 模式验证统一合同。
- 开发客户端完整下载 57,771,664 bytes 后通过哈希、签名和身份校验。
- `0.1.34` Portable 从 HTTPS 签名目录 v67 启动并暂停 Jan 下载；随后同一 Portable 完整下载 Jan 并通过身份校验。
- `0.1.34` Setup 完成隔离安装、启动、关闭到托盘、退出、卸载、注册项清理、数据清理和快捷方式恢复。
- 全量发布测试、生产构建和 30/30 桌面官方源审计通过。

## 剩余人工验收

自动化没有运行 Jan 第三方安装器。仍需用户在日常 Windows 账户中确认 Jan 的安装选项、首次启动、模型数据保留、厂商更新和交互式卸载行为，之后才能把 Jan 从“已审核”标记为“已实机验收”。

## 防复发门禁

Windows 安装包合同必须分别记录：分发文件面向的目标架构、被启动 PE 引导壳的 Machine、安装后主程序架构。文件名、下载路径或厂商页面中的 `x64` 不能代替 PE Machine 实测；封包后必须用指定 Portable 完成至少一个固定安装包的完整身份校验。
