# ADR-0006：双目录视图与独立生态资源商店

状态：已采用

## 背景

同一个厂商可能同时拥有 AI 工具和能够接入 AI 的普通软件。把厂商复制到两套目录会造成名称、图标、官网和启停状态漂移；只给厂商增加一个互斥类型又无法把旗下不同产品正确分流。

早期目录还把 Skill 与 MCP 作为产品详情页的子目录。这个结构无法提供独立的 Skill、MCP 和插件商店，也会把资源的来源产品误认为接收资源的目标产品。同一个资源兼容多个 AI 工具时，复制子目录记录还会产生版本、审核状态和安装策略漂移。

## 决策

活动目录使用 catalog schema v2，并采用以下模型：

1. `Vendor` 只有一份记录。厂商名称、图标、描述、官网、排序和启停不因目录视图重复保存。
2. 每个 `Product.directoryKind` 只能是 `ai-tool` 或 `ai-connectable`，不能同时取两个值。
3. “全部 AI 厂商”由已启用的 `ai-tool` 产品投影；“全部 AI 可接入厂商”由已启用的 `ai-connectable` 产品投影。厂商只有在对应视图存在已启用产品时才出现，且页面只显示该视图的产品。
4. `Product` 不再包含 `extensions`。Skill、MCP 和插件进入顶层 `resources`；每个资源只保存一份。
5. `Resource.resourceTypes` 是由 `skill`、`mcp`、`plugin` 组成的非空数组。一个复合资源可以声明多个类型，但不能为每种类型复制资源身份。
6. `Resource.sourceProductIds` 指向资源所连接、暴露或带入能力的来源产品，例如 Unity MCP 指向 Unity。它不表示资源安装到哪里。
7. `Resource.targets` 保存资源与接收产品之间的多对多关系。每个目标必须独立声明 `productId`、`compatibility`、`moduleId`、`installProfileId` 和 `capabilities`，不能把一个目标产品的配置复制给另一个目标。
8. 资源商店统一按“资源类型 → 目标厂商 → 目标产品”展示。同一资源可以因多个类型或目标出现在多个视图中，但所有入口引用同一个资源 ID 和版本。
9. 后台可以增删改查厂商、产品、资源、来源关系、目标关系、排序和启停；后台只选择客户端公开的固定模块与审核配置，不能提供执行内容。

## 本地执行边界

- `moduleId` 与 `installProfileId` 只是对客户端现有固定能力的引用，不是后台命令。
- 客户端必须重新校验资源、目标产品、兼容性、能力声明和本地审批配置；目录存在目标关系不等于获得执行许可。
- 后台不能下发 EXE、Shell、PowerShell、CMD、任意包名、任意 URL、任意配置片段、任意参数或任意本地路径。
- 资源安装必须在用户明确点击后执行，记录所有权收据，并且卸载只能回收枕星 AI 自己写入的文件和配置项。
- 新增目录记录、兼容关系或现有模块参数不要求重新制作前端；新增本地执行原语仍必须升级客户端并完成独立审核。

## 迁移与兼容

- schema v1 的产品下扩展记录迁移为顶层资源，并把原父产品转成一个目标关系；迁移后不再双写 `Product.extensions`。
- 厂商 ID、产品 ID、资源 ID、安装收据和客户端本地审批身份保持稳定；目录重构不能使已安装内容失去管理能力。
- 旧签名目录保留为不可变历史，不在原版本上改写。schema v2 由新的签名目录版本发布。
- 客户端产品页删除扩展子目录；资源只从相应商店进入，但资源详情仍可链接到来源产品和全部兼容目标。

## 后果

- 同一厂商可以出现在两个目录中而不复制资料，旗下产品在两个页面严格分流。
- Skill、MCP 和插件拥有统一身份、版本与审核状态，并可安全复用于多个目标产品。
- 独立商店可以继续增加资源数量，而不会增加厂商产品统计或拖大产品卡片。
- ADR-0003 中“产品拥有扩展资源子目录”和单一父级展示关系被本决策取代；其客户端适配器、本地白名单和所有权收据边界继续有效。
- ADR-0004 中 Skill/MCP 继续显示在产品子目录的后果被本决策取代；可视化产品聚合入口和 CLI 独立展示的决定继续有效。
